# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BlockChompers is a hyper-casual browser puzzle game built with Three.js (r185) and bundled with Vite 8. Plain JavaScript ES modules, no framework, no TypeScript. v1 is a playable primitive blockout (grid, perimeter track, units, 4xN reserve + 5 parking slots, win/loss); v2 adds feel (direct launch, acceleration, eased motion, final rush); v3 adds a fixed layout, juice (effects, UI animation), a start screen and procedural sound effects, all presentation. The styled Fish of Fortune look is being added in steps: 3D step 1 replaces the units and the track with GLB art exported from Blender, 2D step 1 replaces the flat start screen with key art and an image Play button, and everything else still looks as in v3. `docs/IMPLEMENTATION_PLAN.md` records the v1 design, the step order and the numeric invariants that keep core deterministic (its slot-first launch was replaced in v2: see Locked mechanics below and the README v2 section). Change core behaviour only together with a headless test in `tests/core`.

## Commands

```bash
npm install
npm run dev          # Vite dev server with HMR, http://localhost:5173
npm run build        # production bundle to dist/ (gitignored)
npm run preview      # serve dist/ at http://localhost:4173
npm test             # vitest run (node environment, no DOM)
npm run test:watch
npx vitest run tests/core/GridManager.test.js   # one file
npx vitest run -t "outermost block"             # by test name
npm run export:models    # re-export public/assets/models/*.glb from the .blend files (needs BLENDER_PATH; ART_DIR defaults to ./art)
npm run validate:models  # check the exported GLBs (tests/tools/glb.test.js runs the same checks)
npm run process:ui       # re-process the start screen images (Python + Pillow: PYTHON, else the tools/ui/.venv venv)
```

`npm run build` warns that a chunk exceeds 500 kB. Expected: Three.js is bundled whole. Not a failure.

## Architecture

**Layering rule:** `src/core/**` and `src/config/**` are pure -- no `three`, no DOM, no clock, no randomness. `tests/architecture/no-render-imports.test.js` fails if that is violated, so any test run catches it. It holds `src/ui/layout/**` (the UI's layout math) to the same rule.

- `src/config/Config.js` -- the single frozen config. Core reads `grid/track/units/inventory/rules/timing/progression`; `render` (including `render.audio`), `ui` and `debug` are only for the presentation layers (`src/render`, `src/ui`, `src/audio`). `createConfig(overrides)` deep-merges for tests.
- `src/app/` -- pure, like core (tested in `tests/app`): `AppFlow` is the app state machine MENU (start screen) -> PLAYING; `play()` restarts the current level (Level 1) and `update(dt)` is the only way `main.js` advances the simulation, so nothing steps in MENU. There is no way back to MENU. `Cues.js` names the presentation cues (UI actions and visual moments that are not game events) and holds `CueBus`, an allocation-free emitter.
- `src/core/` -- `GameManager` orchestrates `GridManager` (matrix), `InventoryManager` (units, 4xN reserve, 5 active slots) and `Track` (perimeter math). `ProgressManager` holds money and level progression (`getState()`). `Unit` is dumb data. `easing.js` holds the pure polynomial easing curves that core (acceleration, final rush) and render share. `Simulator.js` holds pure dry-runs over a snapshot. `createGame.js` is the one wiring point used by both `main.js` and the tests. `Sides.js` is the single source of truth for inward directions.
- `src/render/` -- `Renderer` is the Three.js bridge (strictly top-down `OrthographicCamera`); `PrimitiveFactory` is the reskin seam: swap it (same interface) to change the look. Layout is a fixed portrait design (`Config.render.layout`, design units = world units): `layout/computeLayout.js` (pure, tested in `tests/render`) returns every rect, the per-level board cellSize and origin, and the camera view; the camera never refits on a level change and only the board scales. Slots, reserve cells, units and labels keep their layout size on every level. `vfx/` holds the juice: `VfxManager` (event-driven projectiles, block hits, sparks; it borrows blocks and unit positions through Renderer host methods and never touches game state), `VfxFactory` (the ONLY place creating effect geometries and materials: one InstancedMesh per effect type with per-instance colour and opacity, so a look such as the projectile changes there and in render config only) and `ConfettiLayer` (win confetti on its own canvas above the DOM). `anim/` holds pure helpers tested in `tests/render/anim.test.js`: presentation easing (core curves plus overshoot), `Pool` (fixed capacity, recycles the oldest) and `TweenScheduler`. Unit juice (muzzle pop, capacity number swap, death pop) and the counter punch live in the Renderer, which runs a presentation clock: `sync(snapshot, dtMs)`, frozen while paused and scaled by `debug.timeScale`. The Renderer emits the visual cues sounds sync to (block break on impact, capacity tick, unit pop, unit parked, slots empty) on its optional `cues` bus. Effect and juice code must not allocate per frame (reuse Vector3/Matrix4/Color, pooled typed arrays, no per-frame closures). `trackPlacement.js` and `launchPlacement.js` are the pure placement helpers (track path; launch flight, entry queue, return glide), tested headless in `tests/render`.
- Styled look (Fish of Fortune, step 1: 3D only) -- `main.js` awaits `render/assets/AssetLoader.js` (GLTFLoader cache; a file that fails logs an error naming it and that model falls back to its primitive) before building the Renderer with `render/StyledFactory.js`. StyledFactory extends PrimitiveFactory and overrides only `unit()` and `track()`. A unit is a SkeletonUtils fish clone: `render/assets/fitModel.js` (pure) sizes it to fit the one-cell canal, `render/styled/fishTint.js` tints it (one shared `onBeforeCompile` material per palette colour), and its mixer runs on the presentation clock through `group.userData.animator`. The track is InstancedMeshes placed by the pure `render/layout/computeTrackPieces.js`, plus flowing chevrons. GLB meshes sit on `render.lighting.layer`: `Renderer.render()` draws that layer first under the model lights with AgX, then layer 0 exactly as in v3 (v3 lights, no tone mapping, no clear). Blocks, tiles, slots, labels and effects must stay on layer 0, and every model value lives in `render.models` / `render.lighting`. The GLBs in `public/assets/models/` are generated: `tools/blender/models.json` (manifest) and `export_glb.py` (headless Blender, run by `npm run export:models`) cut, flatten and export them in memory. Never edit the GLBs by hand, and never save or move the source .blend files. `tools/glb/inspectGlb.mjs` is a dependency-free GLB parser shared by `validate:models` and the tests.
- Styled start screen (Fish of Fortune, 2D step 1) -- `main.js` also awaits `ui/startScreenArt.js`: both images through `AssetLoader.loadImage` (decoded) and the Titan One `FontFace` via `document.fonts.load`; it resolves null if any fails (the console names the file) and UIManager then builds the flat v3 start screen instead. With the art, UIManager builds the styled screen: a blurred cover copy, the art as the card (`ui.text.title` is only the document title and aria-label), and the Play button as anchor > pulse wrapper > `<button>`, each layer owning one transform (placement, idle breathing, v3 press/release). The pure `ui/layout/computeStartScreenLayout.js` contains the art in the viewport and anchors the button in fractions of the image rect; `ui.resize()` (from main.js) re-applies it. Values live in `Config.ui.startScreen` and reach the stylesheet as `--ui-start-*`. The images come from `tools/ui/process_ui.py` (`npm run process:ui`, settings in `tools/ui/ui_assets.json`) reading `assets/ui/source/*.jfif`; never edit the outputs in `public/assets/ui/` by hand or modify the sources.
- `src/audio/` -- `AudioManager` listens to game events (EventBus) and cues (CueBus) and plays sounds through an sfx gain under one master gain (the Sound toggle mutes it). The AudioContext is created and resumed on the PLAY cue, inside the Play click (autoplay policy). `SfxBank` is the ONLY place defining sounds: procedural Web Audio recipes (oscillators, filtered noise, envelopes) whose numbers live in `Config.render.audio.sounds`, or a file under `render.audio.assetsPath` when a sound's config names one. A voice's nodes disconnect when it ends. `SfxScheduler` (pure, tested in `tests/audio`) decides before any node exists: mute, per-sound `minIntervalMs`, `maxVoices` cap (skip, never queue), combo pitch, jitter. Board sounds play at `debug.timeScale` and follow pause because their triggers do; UI sounds are real time.
- `src/input/InputManager.js` -- pointer -> `renderer.pick` -> `game.activateUnit`. `src/ui/UIManager.js` -- flat DOM UI in `#ui-root`: start screen (while the flow is MENU, styled or flat v3, see above; Play exits, then `flow.play()`), top bar (settings, "Level N", money; hidden in MENU), pause panel (Resume, Restart level, Sound on/off via `SoundPreference.js`), win/lose cards. It renders snapshots, turns clicks into GameManager or AppFlow commands and emits UI cues; it keeps no game state. Effects full/reduced (`EffectsPreference.js`) has no visible option: `render.vfx.effects`, forced to reduced by prefers-reduced-motion. Enter/exit animations use the Web Animations API on transform and opacity only (`Config.ui.anim`); a card's button plays the exit first and then sends its command, and `isAnimating()` keeps the board's input off meanwhile.
- `src/main.js` -- composition root and rAF loop: `flow.update(dt x debug.timeScale)` (steps the game only in PLAYING) -> `getSnapshot()` -> `renderer.sync(snapshot, dtMs)` -> `ui.update(snapshot, realMs)` -> `renderer.render` -> `confetti.update`.

**Contracts**
- Commands in: `activateUnit`, `launchFromSlot`, `pause`, `resume`, `restartLevel`, `continueToNextLevel` return `{ ok, reason }` (the two launch commands never throw; their rejections emit `LAUNCH_REJECTED`). `continueToNextLevel` is the only way to earn money: valid only in WON, pays `progression.rewardPerLevel` once, then loads the next level. The progression is a cycle: after the last level it wraps to Level 1 with the money kept; `getState().isLastLevel` is true on the last level, where the win card says "Play again" (same command). Money is not persisted across page reloads. State out: `getSnapshot()` is plain JSON in cell units with `grid.version` / `inventory.version` counters, plus `paused`, `progress`, `stepAlpha` (fraction of the next step, for render interpolation), `launchSteps`, `finalRush` and `inventory.inUse` / `inventory.available`. Slot changes also emit `SLOT_STATE_CHANGED` (`{ slotIndex, from, to, slots }`; statuses are only `free` and `blocked`), and emptying the reserve emits `FINAL_RUSH_STARTED` once per level. Events out (`src/core/Events.js`) are flushed after each `step()` and are garnish only -- `Renderer.sync(snapshot)` alone must draw a correct picture.
- Fixed timestep: `update(dt)` accumulates into `step()`. `tests/helpers/createTestGame.js` sets speed 1 and fixedStep 1 and turns off the launch flight, eat pause, acceleration and final-rush speed-up, so one `step()` is one cell of travel.
- Coordinates: `matrix[row][col]`, row 0 = top (N), col 0 = left (W); cell-unit origin at the grid's top-left, y down. Only the renderer maps cell units to world, through the level's cellSize and board origin from `src/render/layout/computeLayout.js`.
- Scanning is discrete: `Track.lanesCrossed(tFrom, tTo)` is the only scan trigger, so a lane is scanned exactly once per lap.

**Locked mechanics** (parameterised in `Config.rules` / `Config.track`): one block per lane per pass; one shared track entry point (`entry.corner`); runners keep `track.launchSpacing` between each other along the track (a launching unit waits at the entry for it and a runner waits behind a unit that is eating; 0 = pass-through) and runners move front to back each step (ties: launch order); a lap completes when `distanceTraveled >= length`, never by comparing `t` to `entryT`. Only the front unit of each reserve column can be launched (`inventory.frontOnlyPick`; enforced in core with `NOT_FRONT` and in the renderer, which raycasts only fronts, parked units and blocked slots). When a unit leaves, its column moves up one cell (`RESERVE_SHIFTED`; logic is instant, the renderer animates it with `render.reserveShiftMs` / `reserveShiftStaggerMs`). A launch flies straight to the entry (`LAUNCHING` for `timing.launchToEntryMs`) and needs (moving + parked) < `inventory.activeSlots`; moving units hold no slot, a unit that finishes a lap with capacity left parks in the leftmost free slot, and the "N/5" counter is activeSlots - (moving + parked). A parked unit can be relaunched from its slot (`rules.allowRelaunchParked`, `launchFromSlot`): it keeps its capacity, its slot becomes free at once, and it still counts while it moves. Speed on the track is a pure function of whole-step counters: the acceleration ramp (`units.launchSpeed` -> `track.speed` over `units.accelMs`) times the final-rush factor (1 -> `rules.finalRushSpeedMultiplier` over `rules.finalRushRampMs` once the reserve is empty). LOSE (checked after WIN at the end of every step, fired once): `slots_blocked` when every slot is blocked and nothing moves (`rules.loseMode: 'deadlock'` additionally requires that no parked unit could hit a block), `out_of_units` when the reserve is empty, nothing moves, blocks remain and no parked unit could hit a block. "Could hit" = relaunch allowed and the colour is first on some lane (`GridManager.exposedColors`).

## Levels

`src/core/levels/*.js` export `{ id, grid: number[][], units: [{ color, capacity }] }`. `0` = empty, positive ints = colour ids; zero rows/cols are padding. Level files are pure data (only `id`, `name`, `grid`, `units`; a test enforces it). Ids are content ids (`watermelon`, `starter`), not positions. Colour ids mean different colours per level: their hex values, the scene background and the empty ring/reserve tile colours live in `Config.render.levels[levelId]`, merged over the render defaults (the snapshot carries `levelId`). Every colour a level uses needs a palette entry (tested). The progression is `levels` in `src/core/levels/index.js` (Watermelon -> Panda -> Carrot); `levelLibrary` holds every level, including Starter outside the cycle, and `?level=<id>` (`Config.debug.levelParam`, `src/debug/levelParam.js`) plays any of them on its own.

Reserve design: each unit is sized to what a solo lap can reach once the units before it have finished; Panda and Carrot use the fewest such laps (a search over which colour to launch next). `tests/core/watermelon.test.js` and `tests/core/newLevels.test.js` play each scripted order to WIN under both the test timing and the shipped timing.

`GameManager.validateLevel` runs inside `loadLevel` before any state changes, and every failure is a hard error: grid structure, unit definitions, and **per-colour balance**. For each colour, the units' capacities must sum exactly to that colour's block count, so spare or missing capacity is rejected. As a consequence a level is won only by running every unit down to 0. A unit parks when it finishes its lap with capacity left because its colour is walled in; it blocks its slot until relaunched. With balanced levels and relaunching on, `out_of_units` cannot happen (an exposed colour always has a living, parked unit), so the reachable LOSE is `slots_blocked`. To make a unit park in a test, wall its colour in; never give it spare capacity.

## AI prompt log

`.claude/settings.json` runs `.claude/hooks/log-prompt.js` on every `UserPromptSubmit`; it appends the prompt to `ai_logs/YYYY-MM-DD.txt` (committed). The hook always exits 0 so it can never block a prompt.

## Conventions

- Code, identifiers, comments and the HTML `lang` are English. The project started in Spanish; rename any leftover Spanish names.
- The ids `#canvas-game`, `#ui-root` and `#canvas-fx` (confetti, above the UI) are shared between `index.html` and `src/main.js`; rename both or neither.
- Every tunable lives in `Config.js`, including render layout and all UI copy, colours, sizes (px) and timings (`render`, `ui`). The stylesheet in `index.html` is layout-only; `UIManager` publishes `Config.ui` as CSS custom properties (`--ui-color-*`, `--ui-size-*`) on `#ui-root`. v1 UI rule: plain DOM, solid colours, system font; no images, icon libraries or new dependencies. The styled start screen is the one exception: its processed images and the self-hosted OFL font (`public/assets/fonts/`, no CDN).
- Runners are drawn exactly on the track path: `src/render/trackPlacement.js` interpolates each unit's own `prevDistance` -> `distanceTraveled` by `stepAlpha` and converts it with `Track.positionAt()`. Never offset them sideways; spacing is `track.launchSpacing` along the track. `tests/render/trackPlacement.test.js` checks every drawn runner is on the path. Launch flights, the entry queue and the return glide come from `src/render/launchPlacement.js`; every easing name, duration, damping and curve value lives in `Config` (`render.motionEasing`, `render.rotationDamping`, ...).
